## 2. 产品目标与范围

### 2.1 核心目标

用户上传一张《雀魂》横屏对局截图后，系统在本机完成识别，自动提取自己的手牌和四家牌河。用户可以检查、修改识别结果，确认后将其导入现有牌理引擎进行分析。

第一阶段要解决的是“减少手动录入”，不是实现无人值守的自动对局。

### 2.2 第一阶段范围

- 完整横屏截图上传、拖拽和剪贴板粘贴
- 牌桌定位与透视校正
- 自家手牌切割和牌面分类
- 四家牌河切割和牌面分类
- 红五识别及与现有牌谱格式的兼容
- 每张牌的置信度和原图位置
- 识别结果预览、人工纠错和确认导入
- 本地处理、错误提示和基础回归测试

### 2.3 明确不做

- 不控制 Android 设备
- 不执行点击、登录、匹配、切牌或任何自动游戏操作
- 不在第一阶段识别副露、宝牌、场风、自风、立直、本场、供托或剩余牌数
- 不规划分数识别；后续版本同样不将分数识别列入待办
- 不把用户截图发送到外部 AI 或第三方服务

## 3. 总体技术方案

麻将牌面属于稳定的图形分类问题，主流程采用“传统计算机视觉定位和切割 + CNN 分类”，不以 OCR 作为麻将牌识别方案。后续遇到局数、本场、供托等文字或数字时，再针对特定区域评估 OCR 或小型分类器。

```text
浏览器上传截图
       │
       ▼
本地 Python 识别服务
       │
       ├── 截图有效性检查
       ├── 牌桌检测与透视校正
       ├── 手牌和四家牌河区域切割
       ├── TileNet 批量分类
       └── 置信度、坐标、告警整理
       │
       ▼
结构化识别结果 JSON
       │
       ▼
网页校对界面
       │
       ├── 查看原图识别框
       ├── 修正、删除或补充牌
       └── 用户确认
       │
       ▼
现有 analyzeHand() 牌理分析
```

### 3.1 为什么采用本地 Python 服务

- AutoMajsoul 的识别实现和模型基于 Python、OpenCV 与 PyTorch，迁移成本最低。
- 模型和截图留在本机，更符合个人使用场景和隐私要求。
- 避免首个版本承担模型转 ONNX、浏览器推理兼容性和设备性能适配成本。
- 识别服务与前端解耦，后续可以单独替换模型而不修改牌理引擎。

### 3.2 AutoMajsoul 复用边界

计划复用或改造：

- 牌桌颜色检测和四边形拟合
- 透视变换
- 手牌提取器
- 四家牌河区域提取器
- TileNet 模型结构、预处理逻辑和训练权重

明确不复用：

- ADB 与 `uiautomator2` 设备控制
- 登录及大厅识别
- 游戏按钮识别和点击
- 自动出牌策略
- 自动对局主循环

任何迁入代码必须记录来源和修改内容。AutoMajsoul 使用 CC BY-NC-SA 4.0；当前项目使用 MIT。私人本地开发可以继续进行，但在未来公开或分发整合版本前，必须重新确认衍生代码的许可方式，并完善署名与第三方声明。

## 5. API 与数据契约

### 5.1 接口

```text
GET  /api/health
POST /api/recognize
```

`POST /api/recognize` 第一版仅接受 PNG、JPEG 和 WebP，限制文件大小和像素总量。服务不得永久保存上传图片；调试保存必须通过显式的本地开发配置开启。

### 5.2 返回示例

```json
{
  "schemaVersion": 1,
  "image": {
    "width": 1920,
    "height": 1080
  },
  "hand": [
    {
      "code": "1m",
      "confidence": 0.982,
      "bbox": [120, 840, 52, 76]
    }
  ],
  "rivers": {
    "self": [],
    "right": [],
    "opposite": [],
    "left": []
  },
  "warnings": []
}
```

约定：

- `code` 使用现有前端接受的 `1m`～`9m`、`1p`～`9p`、`1s`～`9s`、`1z`～`7z`。
- 红五使用 `0m`、`0p`、`0s`；导入分析引擎时按五处理，同时保留红牌展示信息。
- `confidence` 范围为 `0`～`1`，不得只返回分类标签。
- `bbox` 为原图坐标 `[x, y, width, height]`。
- 识别不完整时返回已有结果和 `warnings`，不要静默生成看似完整的错误牌局。

## 7. 测试与验收策略

### 7.1 测试层级

- 单元测试：标签转换、坐标变换、切割规则、输入校验和 JSON schema。
- 固定样本回归：同一批截图在代码修改后应保持牌桌定位和麻将牌数量稳定。
- API 测试：健康检查、合法图片、错误文件、超大图片和识别失败。
- 前端测试：上传、取消、纠错、确认导入以及不覆盖原输入。
- 人工验收：不同分辨率、亮度、牌桌皮肤、动画阶段和移动端页面。

### 7.2 MVP 建议指标

- 标准横屏截图的牌桌定位成功率达到可用水平，并记录失败样本，而不是只统计成功样本。
- 单张截图在常用 Mac CPU 上数秒内完成，具体基线在首批样本建立后填写。
- 每一张识别牌都带置信度和坐标。
- 低置信度结果不会被静默自动导入。
- 用户可以在一次校对流程内修复漏牌、错牌和多牌。
- 原有 Node.js 测试全部通过。

现阶段不直接采用 AutoMajsoul README 中报告的准确率作为本项目验收数据；必须使用本项目测试截图重新测量。

## 8. 风险与应对

| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| 游戏皮肤或分辨率变化 | 牌桌、手牌或牌河定位失败 | 建立多样化截图集；保留可视化调试阶段；将硬编码坐标集中配置 |
| 动画、弹窗遮挡牌面 | 错切或错识别 | 返回部分结果与告警；要求用户换一帧；不自动覆盖输入 |
| 原模型训练域较窄 | 新截图分类准确率下降 | 保存低置信度样本；增加数据并微调模型；版本化模型文件 |
| 红五标签处理不一致 | 分析或显示错误 | API 层保留红五，牌理层统一为普通五，并增加专项测试 |
| Python 服务提高启动门槛 | 用户无法直接使用 | 提供依赖锁定、一键启动和清晰健康检查；后续再评估打包 |
| 上游代码许可与 MIT 不一致 | 公开分发存在许可风险 | 保留来源记录；隔离识别模块；公开前完成许可证复核 |
| 私人截图被误提交 | 隐私泄露 | 使用专用私有数据目录并由 `.gitignore` 排除；提交前检查状态 |
